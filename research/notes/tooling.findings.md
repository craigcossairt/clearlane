- [read-on-source] What Claude Science does: Claude writes and runs Python, R or shell code in a sandbox, using persistent kernels. It reads only the folders you grant, pulls data through connectors and can submit jobs over SSH, to Slurm or through Modal. Results are saved as artifacts that carry the code, environment, description and conversation behind them. A background reviewer flags wrong citations, numbers it cannot trace and figures that do not match their code. You approve each new folder, network host and remote job. (https://claude.com/docs/claude-science/overview ; https://www.anthropic.com/news/claude-science-ai-workbench)

- [read-on-source] Claude Code offers five ways to run work in parallel: subagents, agent view (`claude agents`, research preview), agent teams (experimental, off by default), projects (beta on Pro and Max only), and dynamic workflows. Worktrees isolate sessions you run yourself. Agent-view sessions and subagents can each get their own worktree. Agent teams do NOT isolate teammates in worktrees, so the work must be split by file ownership. (https://code.claude.com/docs/en/agents.md)
- [read-on-source] Claude Code dynamic workflows are on all paid plans. They run up to 16 concurrent agents by default (configurable from 1 to 256) and at most 1,000 agents per run. They run in the background and can be resumed in the same session. Claude Code shows a 'Large workflow' warning above 25 agents or about 1.5M projected tokens. (https://code.claude.com/docs/en/workflows.md)
- [read-on-source] Agent teams guidance from the docs: start with 3-5 teammates and give each 5-6 tasks. Two teammates editing the same file overwrite each other. Known limits: no resume for in-process teammates, task status can lag, and split panes need tmux or iTerm2 (Windows Terminal and the VS Code terminal are not supported). (https://code.claude.com/docs/en/agent-teams)

- [read-on-source] Simon Willison: the natural bottleneck with parallel agents is human review. Code built from your own detailed spec is much cheaper to review. Research and proof-of-concept 'scout' tasks parallelize well. (https://simonwillison.net/2025/Oct/5/parallel-coding-agents)
- [read-on-source] Split work along seams, not steps, and do the contract first. Freeze the shared types, schema or API on main, then branch the dependent work from that commit. Aim for disjoint file sets, integrate one reviewed branch at a time in dependency order (contracts, then independent branches, then integrations), and start with 2-3 tasks. (https://parallelcode.app/blog/splitting-work-for-parallel-ai-agents/ ; https://parallelcode.app/blog/ai-coding-agent-best-practices/)
- [read-on-source] arXiv 2610.07261 (Oct 2026 preprint, NP-Bench): giving agents disjoint scopes up front and merging producers before consumers raised clean integration from 1/9 to 9/9 scenarios and cut merge conflicts from 13 to 0. On a live breaking contract change, clean integration went from 0.00 to 1.00 on frontier models (Opus 4.8, GPT-5-Codex). Vague 'a teammate may be editing X' warnings did no better than no coordination. Agents stayed inside their assigned scopes (0 leakage). Caveats: scenarios were hand-built, scopes were hand-seeded, and the samples were small. (https://arxiv.org/html/2610.07261v1)
