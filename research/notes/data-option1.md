

######## data-option1
## SUMMARY
Option 1 can be built for Utah with no API keys. I tested every source below with GET requests on 2026-10-26 (evening, Mountain time).

1. CAISO OASIS returns PacifiCorp East (PACE) data. The node is ELAP_PACE-APND. Tomorrow's (Oct 27) day-ahead hourly prices, which come from the extended day-ahead market PacifiCorp joined (PACE rows start 2026-05-01), run from $21.38 at 3pm Mountain time to $55.78 at 6pm. Each price comes with its congestion component. The same service also has 5-minute real-time prices, PACE's day-ahead load forecast (peak 6,024 MW at 7pm) and a PACE wind and solar forecast. Solar holds about 2.1 GW from 9am to 4pm and falls to 36 MW by 6pm. That evening drop is the rush hour the bounty describes.
2. EIA-930 needs no key for its six-month CSVs or its per-area workbook. PACE.xlsx (75 MB) already holds EIA's hourly CO2 intensity: on Oct 25 it ran from 504 g/kWh at 3-4pm to 817 g/kWh at 7-8am. Those figures lag about a day. An undocumented JSON feed gives PACE demand with about 1.4 hours of lag. The documented v2 API needs a free emailed key.
3. Open-Meteo forecast and archive work for Salt Lake City (CC BY 4.0, non-commercial, under 10,000 calls a day).
4. Electricity Maps lists US-NW-PACE but needs an account. Its free tier is reported as one zone, 24 hours of history and no forecast, but I could not read the official terms. The gridstatus.io hosted API needs a key (500,000 rows a month free). The ERCOT API needs registration plus an ID token that expires hourly; ERCOT's website JSON feeds work without one.

Recommended stack: CAISO OASIS fetched from a server (it sends no CORS headers, returns zip files, allows 31 days per request and about one request per 5 seconds), plus EIA and Open-Meteo, which allow fetching from the browser. Keep a committed snapshot to fall back on. I already built a joined 24-hour PACE file for Oct 27. Both Torus utility customers, PacifiCorp (PACE/PACW) and Portland General Electric, appear in the same day-ahead market data. One data layer can therefore serve both Option 1 and Option 2.
## IMPLICATIONS
- Option 1 for Utah needs no API keys. CAISO OASIS, the EIA-930 static files and JSON, and Open-Meteo cover price, congestion, load, renewables and weather. Reserve a free EIA v2 key (by email) only as a backup to the undocumented JSON feed.
- The 'traffic report for tomorrow' can lead with numbers CAISO publishes the evening before: day-ahead price, congestion component, load forecast and wind/solar forecast for PACE. Our own model then only needs to forecast CO2 intensity, for example by regressing EIA's hourly PACE intensity on EDAM solar, wind and load. That model work is small and defensible.
- Strong demo story from real data: tomorrow PACE solar falls from about 2.1 GW to 36 MW between 4pm and 6pm MT, the price jumps from $21-22 to $55.78, and load peaks at 7pm MT. Oct 25's 504 vs 817 g/kWh shows the clean window. That makes '6-9pm MT is rush hour; shift to 10am-4pm' concrete.
- Torus tie: PacifiCorp (PACE/PACW) and Portland General Electric are both Torus utility customers, and both sit in the same 4-area EDAM data feed as CAISO. A simulated Torus Station (flywheel plus battery) at a Utah manufacturing site can be valued on real PACE price spreads and congestion components. Feeder-level congestion stays simulated and labeled.
- Overlap with Option 2: the same PACE/PACW/PGE/CISO day-ahead prices and carbon intensities can rank where and when a movable compute job should run. Build one data layer and reuse it for a 'job router' view if time allows.
- Architecture: one small backend job (Python or Node) fetches OASIS (no CORS, zip, 31-day cap, about 5 s between requests) and the EIA files, writes JSON to cache or the repo, and the frontend reads only that JSON. Open-Meteo and the EIA 930-api can also be called directly from the browser (CORS open).
- Skip Electricity Maps and the gridstatus.io hosted API: both need accounts and neither adds PACE data that EIA lacks. ERCOT and CAISO-only views can come from no-key website feeds. A direct ERCOT API integration costs a registration and a token flow for a comparison panel.
- The gridstatus library is optional: useful in a Python data-prep script (CAISO methods need no key), but about 54 MB of dependencies, and its EIA class insists on a key. Four direct HTTP fetchers are simpler for a 44-hour build.
- Fallback plan: (1) Monday night, pull and commit a snapshot of the last 31 days of PACE/PACW/PGE/SP15 day-ahead prices and components, hourly real-time prices, PACE.xlsx parsed to a small CSV (CO2 plus fuel mix, last 90 days), the EIA six-month file filtered to PACE/PACW/PGE/CISO/ERCO, and Open-Meteo. (2) Tuesday night about 9pm MT, pull Wednesday's day-ahead prices and forecasts and freeze them as the 'demo day' bundle. (3) Run the app with DATA_MODE=live|snapshot, falling back to snapshot when a request fails or exceeds about 5 s, and show a 'Snapshot as of <timestamp>' badge. A first joined bundle already exists at <research scratchpad>/research/data/pace_snapshot_2026-10-27.csv
## RISKS
- OASIS rate limits are undocumented (about 1 request per 5 s, HTTP 429), and GroupZip can answer 'in processing, retry later'. Never call it from the browser or once per user; cache on the server.
- The EIA 930-api JSON and the ERCOT and CAISO website feeds are undocumented and could change or block us during the demo. The snapshot fallback covers this.
- EIA CO2 intensity lags about 1 day (consumed basis about 2), so 'live' carbon numbers must be a nowcast or forecast and labeled as such.
- Time zones: OASIS gives GMT timestamps with Pacific hour-ending OPR_HR, EIA files use Mountain local time, and Open-Meteo returns whatever timezone is requested with radiation labeled by the end of the hour. Join everything on UTC interval-start. DST ends Nov 1, after judging.
- EIA-930 has imputed values and small negative night solar; clamp them, and prefer the 'Adjusted' columns where present.
- PACE is mostly a net exporter, so generated and consumed carbon intensity differ. Pick one and say which on screen.
- EDAM has only about 6 months of PACE day-ahead history (from 2026-05-01). Longer price history must come from real-time WEIM prices.
- No public feeder or hosting-capacity data was found for Rocky Mountain Power. Any feeder-congestion view is simulated and must say so (rules allow labeled simulation).
- Open-Meteo's free API is non-commercial with CC BY 4.0 attribution. Fine for a hackathon; credit it on screen.
- Tooling: the Parallel Search free tier and Firecrawl keyless daily limits were hit mid-task, so official Electricity Maps and gridstatus.io pricing pages could not be read and those claims stay unverified.
## OPEN QUESTIONS
- When exactly does CAISO publish day-ahead (EDAM) results each day? This sets when to schedule Tuesday's pre-fetch of Wednesday's data. Observed only: Oct 27 data was available by about 8:16pm PT Oct 26, and the wind/solar file was published 9:10am PT.
- Official Electricity Maps free-tier terms in 2026 (zones, history, forecasts). Only third-party summaries were readable.
- gridstatus.io's exact rate limits, and whether its hosted catalog includes EIA-930 PACE and the EDAM datasets.
- Does EIA API v2 expose the CO2 emissions series as a route? Not checked, because it needs a key.
- Does Rocky Mountain Power publish any feeder-level hosting-capacity data that could replace the simulated feeder layer?
- Should the demo stay Utah-only (PACE) for the Torus judges, or show PACE next to PACW/PGE/CAISO, which also sets up the Option 2 overlap?
